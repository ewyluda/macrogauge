## F1 — P2: A valid null power block now breaks the site typecheck

**Location:** `site/src/app/datacenter/page.tsx:218` (`dc.power?.hubs.length`).

The page imports `datacenter.json` directly, so TypeScript infers the shape from that particular JSON file. If the artifact contains `"power": null`, the optional chain's non-null branch is `never`, and accessing `hubs` raises **TS2339: Property 'hubs' does not exist on type 'never'**. Optional chaining prevents a JavaScript exception but does not widen the imported JSON type.

This is a supported input: `schemas/datacenter.schema.json` explicitly allows null power, and `pipeline/engine/dcindex.py:power_block` returns `None` when no configured wholesale hub has store observations. It can occur on a bootstrap publish; it is not a claim that the current production artifact is null.

**Evidence:** supply the checked-in artifact with only `power` changed to null through a virtual TypeScript compiler host. The PR head produces exactly the error above; the base revision produces zero errors with the same fixture. The fixture passes the published JSON schema. Since `next build` checks types, this prevents exporting the entire site for that valid data state, even though the conditional rendering would hide the section.

**Suggested correction:** read the artifact through its schema type or reuse a `PowerData | null` variable for both the summary and hub count. Add a compiler/build regression case using null power; the existing `powerSummary(null)` unit test does not exercise JSON type inference at this call site.

## F2 — P2: The power summary assigns an unrelated hub's date to older headline data

**Locations:** `site/src/app/power/page.tsx:44–49,61–63`; related summary at `site/src/app/datacenter/page.tsx:203–206`.

The new page takes the maximum observation date across all hubs and calls it “Updated,” while its featured quote is selected by YoY change and has no displayed observation date. These dates are neither the page's publication time nor necessarily the selected hub's date. Day-ahead delivery dates can also be later than publication.

**Evidence on the committed artifact and in Chromium:**

| Meaning | Value |
| --- | --- |
| Artifact publication | October 7, 2026, `18:51:57Z` |
| Featured hub | PJM Western Hub |
| Featured hub's actual observation/window end | September 29, 2026 |
| Featured reading | `$85.72/MWh`, `+61.9%` YoY |
| New page's update label | **Updated Oct 8, 2026** |
| Source of that update date | ERCOT's October 8 day-ahead observation |
| Featured KPI's wording | **the hottest hub this month** |

Thus September-window figures are presented as this month's featured reading under a future update label. A failed individual hub refresh can retain the same old winner while other hubs advance; the `StaleBanner` compares artifact publication timestamps and does not detect this source-level aging. The detailed table still shows each hub's own date, but the new summaries discard it.

**Suggested correction:** use `published_at` for a label describing publication; show `sum.hub.asof` alongside the featured average/YoY and retain that context on the hub page too. If the headline promises current observations, filter or qualify aged sources and avoid claiming a common “this month” comparison when windows differ. If displaying the newest delivery date, label it as such instead of “Updated.”

## F3 — P2: The summary drops PJM capacity when optional market detail is absent

**Location:** `site/src/lib/dcHub.ts:61–67`.

`powerSummary` only reads `capacity_markets`. That property is optional in both the published schema and `PowerData`, while `capacity_auction` is required and carries the original PJM auction history. The existing `PowerPanel` explicitly supports this shape by mapping `capacity_auction.rows` into a PJM market when detailed markets are absent or empty. The new helper has no equivalent fallback.

**Evidence:** remove only `capacity_markets` from the committed artifact. It still passes schema validation and retains the latest PJM price of `$325/MW-day`. `powerSummary` returns `capacity: null`, suppressing the headline capacity card on both pages, while the detailed `PowerPanel` still renders the `$325` price. An empty `capacity_markets` array has the same problem.

**Suggested correction:** share the existing market normalization/fallback between the summary and detailed panel. Test both omitted and empty optional market lists. This is a supported-artifact compatibility regression, not missing underlying data.

## F4 — P2: Headline availability incorrectly controls whether the power section exists

**Location:** `site/src/app/datacenter/page.tsx:199–201`.

The old section rendered whenever `power` existed. The new section renders only when `powerSum.headline` is non-null. The helper can legitimately return no sentence despite having useful capacity, tariff and hub-level data: it requires a hub with a YoY reading or at least a doubling in capacity price. A publish without sufficient prior-year hub history and with a capacity multiple below two removes the whole section.

**Evidence:** a schema-valid fixture with null hub YoYs, a PJM capacity move from `$100` to `$150`, and all 17 tariff rows returns a `$150` capacity summary and a tariff count of 17, but rendering the actual datacenter page produces no `id="dc-power"`. Its fixed jump bar still contains `href="#dc-power"`, so the Power jump also stops working. This fixture retains `capacity_markets`; it is independent of F3's legacy fallback defect.

**Suggested correction:** base section existence on available power data, and make only the optional takeaway conditional. Use the stable “The power bill” heading when no quantitative sentence is supported; keep available cards and the detail link.
