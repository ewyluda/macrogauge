## P2 — Medium priority

### F2 — A partially observed roster is mistaken for the complete new roster

Location: `pipeline/publish/compute.py:144–150`; upstream omission at `196–201`.

`_model_rows` omits never-observed models from `members`, and `_index` constructs `current` from the nonempty members it receives. Consequently, `first_full(current)` means all *observed* new models, rather than all eight configured new models. A successful partial OpenRouter response is explicitly allowed by that connector.

Controlled reproduction: six retired models have observations through October 6; only one current model is priced on October 7 and 8. Seven current table rows are null. The writer nevertheless declares October 7 the new full-roster base, removes the six retired members after that day, and publishes:

```text
dates:   Oct 5, Oct 6, Oct 7, Oct 8
members:     6,     6,     7,     1
index:     100,   100,   100,  null
as_of: Oct 7
```

The old observations are still within their seven-day carry window, so the intended incomplete-roster fallback could have continued. With three to seven new models, the same error can silently rebase on a smaller roster instead of visibly freezing.

Pass the configured expected membership separately from the available price histories, or retain empty histories and require every configured model before retiring the predecessor basket. Cover models that have *never* been observed; the new alternating-days test gives every model some data and misses this case.

### F3 — An eight-day gap can permanently null the token index after recovery

Location: `pipeline/publish/compute.py:145–152` (choosing the new base), interacting with `157–180` (carry limits and common-member links).

The old series are removed from collection, and their final prices carry for only seven days. If the first successful collection of the new roster occurs eight or more days after the final old-roster observation, there are no common members to bridge the two baskets. The chaining loop keeps `prev` on the last old date indefinitely. Every later new date fails the same common-member test even when all eight new models have fresh prices.

Controlled reproduction: old prices through October 6; all eight new models priced October 14, 15, and 16. The writer selects `base_date = 2026-10-14`, but no chained level exists for that date. It then publishes **every historical index value as null**, including October 5–6, plus `value = null` and `as_of = null`. The schema still validates these nulls, and the compute phase's completion check does not establish that the series recovered.

This is a distinct problem from F2: the new roster is complete here. Avoid committing a handoff without a valid overlapping link. If overlap cannot be recovered, handle an explicit break/restart rather than choosing an unreachable base and erasing the usable earlier history. Test an initial source outage that exceeds the predecessor carry window and several subsequent successful collections.

### F4 — Expired quotes remain eligible for the current-price recommendation

Locations: `site/src/lib/cloudGpu.ts:21–29`, `37–44`; rendering at `site/src/app/compute/page.tsx:130–140`; writer at `pipeline/publish/compute.py:227–237`.

The cloud writer retains the last observation indefinitely. The pivot accepts every non-null value, irrespective of its date, and computes the cheapest quote and headline range from it. The marketplace comparison likewise drops the observation date. Although a cloud cell has its date in a `title` attribute, the table and takeaway contain no visible freshness qualification. The page shell's general advisory indicator does not identify which comparison cells are stale.

A synthetic October 21 publish containing an October 7 AWS quote of $6.88, a fresh Azure quote of $12.29, and an October 7 vast.ai median of $1.92 renders:

```text
An H100 lists at $6.88–$12.29 per GPU-hour across 2 clouds,
against a $1.92 vast.ai marketplace median.
```

The expired AWS quote is still bolded as cheapest. Rendering the actual page confirms that October 7 is absent from the visible cloud section; it appears only in the hover attribute. These example prices are fixture values used to demonstrate behavior, not a claim about an October 21 market.

Apply the registered freshness limit before including quotes in current ranges/rankings, and preserve marketplace dates. If retaining old observations for context, label them visibly as stale with their dates and exclude them from an unqualified current-price recommendation. Cover provider-specific failures and stale marketplace data, not just null prices.

### F5 — The A100 price row compares 40 GB and 80 GB GPUs without disclosure

Location: `pipeline/publish/compute.py:73`, `78`, `81` (all grouped under `A100`); pivot at `site/src/lib/cloudGpu.ts:23–29`.

AWS is represented by `p4d.24xlarge`, whose eight A100 GPUs each have **40 GB** of memory. CoreWeave's recorded and current A100 row has **80 GB** per GPU. Both become the same unlabeled `A100` comparison row and compete for the same cheapest-price emphasis. The data contract carries no VRAM field; the page only prints the AWS instance identifier, which does not explain the capacity difference to the reader.

The capacities are confirmed by [AWS's instance specifications](https://docs.aws.amazon.com/ec2/latest/instancetypes/ac.html) and [CoreWeave's pricing table](https://www.coreweave.com/pricing). AWS lists `p4de.24xlarge` as the 80 GB alternative, but this review does not assume its current availability or price.

Memory capacity is a material distinction for whether a model fits and how many GPUs a workload needs. Split A100 rows by memory variant, label the differing variants explicitly, or select a verified comparable variant. Do not present one lowest-price ranking as if these were interchangeable configurations.

## P3 — Low priority

### F6 — The methodology copy incorrectly says spot rates are not published per SKU

Location: `site/src/app/compute/page.tsx:150–151`.

The sentence groups reserved, committed-use, and spot prices together and says they are not published per SKU. The PR's own `coreweave_pricing.html` contains a labeled H100 spot price, and the Azure fixture includes SKU-specific spot/low-priority meters that the connector intentionally excludes. [CoreWeave's live page](https://www.coreweave.com/pricing) publishes the spot column, while the [Azure API documentation](https://learn.microsoft.com/en-us/rest/api/cost-management/retail-prices/azure-retail-prices) documents spot and reservation price responses.

Clarify that these pricing modes are excluded from this comparison. Separate negotiated discounts from publicly published spot/reservation rates, and avoid implying that a buyer cannot obtain those quotes.
