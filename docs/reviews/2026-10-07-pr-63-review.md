## F1 — P2: The backlog explanation claims more about demand than the inputs establish

**Location:** `site/src/app/longlead/page.tsx:269–271`; related annotation at line 264 and publisher comment at `pipeline/publish/longlead.py:87–88`.

The new methodology tells readers that a falling backlog ratio with a flat order book means factories are shipping faster and rules out cooling demand. The chart annotation also abbreviates *unfilled orders* to *orders*. These are different quantities: the balance of outstanding orders does not establish the direction of incoming orders.

The [Census M3 definitions](https://www.census.gov/manufacturing/m3/definitions/index.html) describe the relationship as ending backlog = beginning backlog + net new orders − shipments. The two YoY inputs added here contain neither the beginning-of-month backlog change nor net new orders. Shipments are dollar values, so their growth also need not represent faster physical production.

**Counterexample:** these two monthly states satisfy that accounting identity exactly:

| State | Beginning backlog | Net new orders | Shipments | Ending backlog | Backlog / shipments |
| --- | ---: | ---: | ---: | ---: | ---: |
| Year-ago month | 100 | 100 | 100 | 100 | 1.00 |
| Current month | 150 | 70 | 120 | 100 | 0.83 |

The new page's condition is satisfied: shipments are up 20%, ending backlog is unchanged, and the ratio falls. Yet new orders fall 30%. This demonstrates a flaw in the general inference; it is **not** a claim that current turbine demand has fallen.

The checked-in store does support the narrower historical explanation: turbine shipments decline from 3,924 in October 2019 to 2,894 in April 2020, while unfilled orders move from 31,249 to 32,077. The ratio spike and its denominator explanation are not themselves findings. The issue is converting that observation into a demand verdict.

**Correction:** name the stock explicitly as *unfilled orders*, describe the measured numerator/denominator changes, and say that the ratio alone cannot determine whether new demand cooled. A demand conclusion needs separate evidence about new orders, cancellations, and relevant price or mix effects.

## F2 — P2: A partial source refresh removes every survey date from the headline

**Location:** `site/src/lib/longLead.ts:103–110`; the result also populates page metadata at `site/src/app/longlead/page.tsx:27`.

`leadTakeaway` appends a period and basis only if **every** weeks-based figure shares both. When just one package is updated to a different period or source basis, `when` becomes an empty string. The old and new numbers then appear together without any observation dates or basis labels. The vendor-horizon branch also omits its date unconditionally, including the current Caterpillar entry.

**Evidence:** start from the real config and update only switchgear's period/as-of to Q2 2026/August 4, 2026. The loader accepts the config and the publisher produces a schema-valid artifact. Transformers remain Q2 2025. The resulting headline contains the same 143-, 128-, and 44-week values but contains **neither Q2 2025 nor Q2 2026**. This is a simulated ordinary partial curation update, not a claim that a new switchgear source has published those values.

With today's config, the CAT headline clause likewise states its 2028 horizon without its Q2 2026/August 2026 context. The detailed rows retain dates, but that does not correct the headline or browser/search title, which can be read independently.

**Correction:** retain each figure's period and basis when they differ, or group only readings that actually share them. Date the vendor-horizon clause too. Add mixed-period, mixed-basis, and vendor-only cases; the current headline test covers one shared survey period only.

## F3 — P2: A zero year-ago unfilled-order balance now aborts the board refresh

**Location:** `pipeline/publish/longlead.py:89–91`.

The new unfilled-orders percentage divides by `uo[year_ago]`. The preceding guard only establishes that the old **ratio** exists; that ratio can validly be zero when unfilled orders are zero and shipments are positive. `prev is not None` therefore does not make the new denominator safe.

**Evidence:** an in-memory vintage-store fixture with year-ago unfilled orders/shipments of `0/100` and current values of `600/100` returns backlog ratios `[0.0, 6.0]` and a 6.0-month annual change on the pinned base revision. The PR head raises `ZeroDivisionError: float division by zero` on the identical rows.

`run_daily._longlead_phase` calls this function before building/writing the artifact. The phase-level exception handling consequently prevents the **whole long-lead board**, including unrelated curated vendor and lead-time updates, from refreshing. Other phases are isolated; this is not an entire-pipeline outage. The committed electrical/turbine histories currently contain no zero balances, so the finding is conditional on this accepted numeric input or a source anomaly.

**Correction:** guard each percentage-change denominator independently. Omit an undefined leg, or make it explicitly nullable in the schema, while preserving the valid ratio series and other board data. The existing `pipeline.publish.util.yoy_pct` already demonstrates zero-base handling elsewhere.

## F4 — P3: The benchmark's stale flag never reaches the page

**Location:** `site/src/app/longlead/page.tsx:253–255`.

The writer computes `lead_time_benchmark.stale`, but the benchmark's only display renders the number and link without inspecting that flag. Package lead times get an explicit stale badge; the all-equipment benchmark silently keeps the same current-tense presentation after it expires.

**Evidence:** publish the unchanged config as of April 1, 2027. The JLL benchmark is `stale: true` under the PR's 430-day rule, but rendering the actual page still shows the 42-week US average with no stale qualification. Its first stale date is March 13, 2027. The source link's label does include January 6, 2026, which mitigates the problem, but a visible source date is not the promised stale status. A fresh daily publication also prevents the page-level `StaleBanner` from catching this source-level aging.

**Correction:** render the benchmark's stale status beside its number, consistent with package rows, and identify it as a historical reported average when stale. Cover a freshly published artifact carrying an aged benchmark.

## F5 — P3: The stacked mobile board still pushes vendor text off a narrow screen

**Location:** `site/src/app/research.css:729–736`, particularly the switch to `overflow: visible` at line 730.

The responsive rules stack the cells but retain the existing `.research-page .data-table td:last-child { white-space: nowrap; }`. Long vendor lines therefore cannot wrap. Changing the table container to visible overflow lets those lines extend the document beyond the viewport.

**Evidence in Chromium, using both the committed artifact and the built new-data preview:**

- At 390px, the existing test passes and document width is 390px.
- At 320px, document width becomes **330px**. The table has `clientWidth: 278` and `scrollWidth: 309`; the Schneider Electric line's text ends at x = **330.046875px**.
- A temporary browser-only rule setting the last vendor cell to `white-space: normal` removes the overflow. No source fix was applied.

The added test only exercises 390px and checks the cell's bounding box rather than its text bounds. It misses the narrow-width failure because a grid cell can fit while its unwrapped contents overflow.

**Correction:** allow vendor text to wrap within the stacked mobile cells. Add a 320px reflow check using document/content overflow, retaining the existing 390px case.
