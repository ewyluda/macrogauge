## Finding, highest severity first

### 1. P2 — Preserve FRED IDs for the December 2016 CPI backfill

**Changed location:** [config/series.json:70–73](https://github.com/ewyluda/macrogauge/blob/c9724a992ce7df63714da95ba49b378da813958b/config/series.json#L70-L73), also line 49. **Affected consumer:** [scripts/backfill_base_dec2016.py:30–40](https://github.com/ewyluda/macrogauge/blob/c9724a992ce7df63714da95ba49b378da813958b/scripts/backfill_base_dec2016.py#L30-L40).

The source migration changes provider IDs that `backfill_base_dec2016.py` still sends directly to `fred.fetch`. The construction backfill was adapted in this PR, but this CPI backfill was missed. Its headline request now uses `CUUR0000SA0` instead of `CPIAUCNS`, and the medical, apparel, education, and recreation requests use BLS IDs instead of FRED's aliases (`CPIMEDNS`, `CPIAPPNS`, `CPIEDUNS`, and `CPIRECNS`).

Running the actual backfill against an injected FRED endpoint with the pre-migration ID contract yields:

| Registry | Requested | Stored December bases | Exit code |
| --- | ---: | ---: | ---: |
| Before PR | 14 | 14 | 0 |
| PR head | 14 | 9 | 0 |

The missing codes are `CPIAUCNS`, `CUUR0000SAM`, `CUUR0000SAA`, `CUUR0000SAE`, and `CUUR0000SAR`. FRED's connector tolerates individual failures, so the script warns and prints `9 Dec-2016 rows fetched, 9 new`, then returns success. Independent public-page checks on October 15 returned HTTP 404 for `CUUR0000SA0` and `CUUR0000SAM`, and HTTP 200 for [FRED's medical-care alias, CPIMEDNS](https://fred.stlouisfed.org/series/CPIMEDNS).

**Impact:** rebuilding or repairing a store without those December 2016 observations no longer restores the complete CPI residual base. Using the real stored histories with only these failed bases removed, `derived.residual_index` starts in January 2017 at `100.0` instead of December 2016 at `100.0`; the correctly based January value is `100.64347791858788`. The current committed store already contains the bases, so existing production history is not deleted by this PR. The regression affects the supported recovery/backfill path.

**Correction:** retain an explicit FRED mapping for this backfill, or adapt it to a provider-aware historical fetch. Using internal codes directly is insufficient for the four component aliases. Require all 14 December observations before writing, and add a regression test asserting complete coverage with the new registry and no writes when any required base is unavailable.

## Resolution

**Finding 1 confirmed and fixed.** `backfill_base_dec2016.py` built its FRED request from `source_id`, which the PR changed to BLS IDs.

- **Durable fix.** Each registry entry for a series collected from another provider now carries `fred_id`, the pre-migration FRED ID. `Series.fred_series_id` returns the ID that FRED and ALFRED know, regardless of which provider collects the series daily. `load_registry` rejects `fred_id` on a FRED-sourced series.
- **Every FRED/ALFRED tool that can receive a migrated series now uses that ID:**
  - `backfill_base_dec2016` also refuses to write unless all 14 December 2016 bases return.
  - `backfill_construction_mix` replaces the earlier code-as-ID shortcut and remaps rows to codes.
  - `backfill_dc_vintages --codes` now resolves FRED IDs as well.
  - `backfill_dc_history`, `backfill_uo_history` and `backfill_leadlag_target_history` already refuse non-FRED series. `backfill_alfred` takes raw FRED IDs.
- **Tests added:**
  - `tests/test_backfill_base_dec2016.py` checks that, with the real registry, FRED receives exactly the 14 FRED IDs (including the five aliases) and all 14 bases are stored. If one base is missing, the backfill exits and writes nothing. Both tests fail on `c9724a9`.
  - The registry pin covers the FRED ID of every BLS-collected series.
  - An ALFRED `--codes CUUR0000SAM` test checks that ALFRED is asked for `CPIMEDNS`.
- **Reproduction.** The harness above now fails at its "bug present" assertion, as intended. With that assertion removed, the PR head plus the fix gives: after `requested 14, stored 14, rejected []`; residual starts 2016-12-01; January 2017 = `100.64347791858788`, the same as before the PR. The migration and refusal controls are unchanged.
- `pytest -q`: 1,355 passed.
