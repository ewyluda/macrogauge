## F1 — P2: Multi-year histories appear under the three-month trend heading

**Locations at the reviewed head:** `pipeline/publish/commodities.py:102,123`; displayed by `site/src/app/commodities/page.tsx:118,139–143`.

The writer now adds monthly steel PPI and annual PJM capacity auctions to a table whose sparkline column still says **“3-mo trend.”** The daily-series convention of taking 60 observations does not describe three months for these additions. The capacity writer likewise returns the entire auction history without giving the frontend a separate trend period.

**Offline reproduction using the saved store and current configuration:**

| New row | Sparkline content | Displayed column heading |
| --- | --- | --- |
| Steel mill products (PPI) | 60 monthly points, September 2021–August 2026; first value 418.47, latest 381.162 | 3-mo trend |
| PJM capacity, auction clearing (2028/29) | Five delivery-year auctions, 2024/25–2028/29; first price $28.92/MW-day, latest $325/MW-day | 3-mo trend |

The regenerated artifact validates against the PR schema. Rendering the actual page with that artifact confirms both histories appear in the three-month column. The accessible sparkline descriptions identify point counts but do not disclose their date ranges. The footer's reference to the last 60 observations does not correct the misleading column heading or explain the capacity series' different basis.

**Impact:** readers can interpret multi-year steel and auction-price movements as changes over the past three months and compare them with adjacent daily-price trends on that incorrect basis.

**Correction:** carry and display accurate per-row trend periods, or use a neutral history heading with explicit monthly and delivery-year labels. If retaining a three-month chart for daily/monthly observations, select by date rather than a universal observation count and present capacity auction history separately.

## F2 — P3: The browser test does not exercise stand-in labels on the committed artifact

**Location at the reviewed head:** `site/e2e/research-refresh.spec.ts:345–347`.

The test derives its stand-in rows from the committed `commodities.json`, then makes label assertions only inside a loop. That artifact contains **zero `chg_alt` rows**, so the new test passes with zero stand-in assertions. The regenerated artifact contains five: DDR5, DDR4, NAND, H100-hour, and PJM capacity. The current test therefore does not establish that the newly introduced `YoyCell` stand-in branch works.

There is a second coverage weakness in the same assertion: it searches the entire page and uses `.first()`. DDR5, DDR4, and H100-hour all have the label `since Jul 15, 2026`. After the new data publishes, one visible instance can satisfy the assertions for all three rows even if two omit their own labels. The assertion also does not verify the associated percentage.

**Evidence:** the targeted Playwright test passed against the reviewed static export. Independently counting the loop's inputs produced zero rows for the committed artifact and five for the regenerated artifact. Server-rendering the page with the regenerated artifact produced five stand-in cells, confirming that the feature is reachable with the new publisher output but absent from this browser test's current data.

**Correction:** exercise a deterministic, nonempty fixture containing the new rows, assert the expected stand-in codes, and scope each percentage-and-label check to its corresponding table row. Since the page imports JSON at build time, provide the fixture before building or through a component-test seam; intercepting a subsequent browser fetch alone will not change the rendered table. If retaining a publish-dependent test, explicitly mark the unavailable case rather than treating zero assertions as coverage.
